# サイトの使い方

デプロイした Automation App を画面から操作して、AI にやってもらう ToDo を1件書き、Agent を作り、動かし、止め、ToDo を閉じるまでの手順である。
デプロイ自体は[README](../README.md)にある。
同じ内容を短くしたものが、ログイン後の画面の「使い方」（`/guide`）にある。

## 1. 前提

必要なものは3つである。

- Automation App の URL：`scripts/deploy-gcp-guide.sh` が最後に表示する。あとから調べるなら `terraform -chdir=infra/envs/demo output -json service_urls` である。
- ログイン情報：`testuser` または `otheruser`。パスワードはどちらも `password` である。この2人は `apps/human-idp/src/oidc/store.ts` が持つ固定ユーザーで、追加はできない。
- ログインユーザーへの Human Permission：`scripts/deploy-gcp-guide.sh` が `document.read`、`document.write`、`finance.payment.read`、`finance.payment.approve` を付ける。

Human Permission が空のままだと、ログインはできても権限決定がすべて却下になり、Agent を1つも作れない。
`GRANT_DEMO_PERMISSIONS=0` でデプロイした場合や、あとから増減させたい場合は次のコマンドで付け外しする。

```bash
GOOGLE_CLOUD_PROJECT=<project-id> STORE_MODE=gcp PUBSUB_MODE=gcp \
  pnpm perm:set <testuser|otheruser> <capability_id> <grant|revoke>
```

## 2. 全体の流れ

| 段階 | 画面 | 押すもの | そこで決まること |
|---|---|---|---|
| 1 | `/` | 「ToDo を登録する」 | AI に何をさせたいか（ToDo ＝ Work Definition） |
| 2 | `/` | 「この内容で確定する」 | ToDo の内容が固まる。以後は書き換えられない |
| 3 | `/` | 「必要な権限を調べる」 | その ToDo に許可される操作と隔離のレベル（Agent Definition） |
| 4 | `/` | 「この権限で承認する」 | 提示された権限への同意 |
| 5 | `/` | 「この内容で Agent を作る」 | Agent が作られ、ToDo の実行を始める。ToDo は「実行中」になる |
| 6 | `/agents/{agent_id}` | 「指示を追加する」「この Agent を止める」 | 実行中の Agent への追加指示と停止 |
| 7 | `/` | 「完了にする」「取り下げる」 | ToDo を閉じる |
| 8 | `/activity` | Task をクリック | 終わった処理の再生 |
| 9 | Analysis Console | 読むだけ | ログを分析するエージェントが自分の Agent をどう見ているか |

段階1から5と7は、ログイン後に開く1枚の画面（`/`）の中で上から下へ進む。
ToDo は画面のほかに、外部のツールから API で登録することもできる（§7.5）。

## 3. ログインする

Automation App の URL を開くと Human IdP のログイン画面へ飛ぶ。
ユーザー名とパスワードを入れると、必要な権限を全部並べた同意画面が1枚出る。
そこに出る `agent:operate`、`workdef:submit`、`agent:provision`、`agent:revoke` が、この画面が以後あなたの代わりに行える操作の全部である。
同意すると認可要求が続けて5回走る。
最初の1回で ID Token を取り、残りの4回で Automation App、Authorization Platform、Agent Provisioner、Lifecycle Manager それぞれ宛のアクセストークンを取る。
アクセストークンは1枚につき宛先1つと権限1つで、同意済みなので2回目以降は画面が出ない。
パスワードと同意を聞かれるのは最初の1回だけで、画面が何度か切り替わるのはこのためである。

戻ってきた先が「ToDo」の画面である。

## 4. ToDo を書いて確定する

「1. ToDo を書く」に、AI にやってもらいたいことを1件書く。

| 欄 | 書くこと |
|---|---|
| タイトル | 何をするか、一言で。必須 |
| 説明 | 何をしてほしいか |
| 実行時のコンテキスト | 背景、前提、関係する資料の場所など、AI が作業中に持っていてほしいこと。ここに書いた内容は Agent への最初の指示に載り、権限の判定には使われない |
| 完了条件 | 何ができたら終わりか。1行に1つ。AI はこれを満たしたら作業を終える |
| 手順 | 1行に1つ。任せてよければ空でよい |
| 注意点・やってはいけないこと | 1行に1つ |
| 優先度 | 高・中・低。一覧の並び順に使われ、AI にも伝わる |
| 期限 | 日付。一覧の並び順に使われ、過ぎると「期限切れ」と出る。AI にも伝わる |
| 希望する稼働時間 | 分。1分から1440分（24時間）までで、この範囲を外れる値は登録の時点で断られる |

何を書くか決まっていないときは、画面の上にある「ToDo の候補を探す」に期間を入れる。
その期間に記録されている作業から、AI に任せられそうなものを挙げる。

**この画面に権限を書く欄は無い**。
何を許可するかは書いた ToDo の内容から決まるもので、利用者が先に指定するものではない（[03. 権限決定](./03-authorization.md)）。

登録すると「2. ToDo 一覧」に「下書き」として並ぶ。
直したいところがあれば「書き直してもらう」に文章で伝えると、AI が書き直した案が同じ場所に反映される。
自分で直すなら「自分で書き直す」を開く。
どちらも文面を書き換えるだけで、確定させる操作ではない。

「この内容で確定する」を押すと ToDo は「実行待ち」になり、内容は書き換えられなくなる。
やらせないと決めたら「取り下げる」で閉じる。取り下げた ToDo は元に戻せない。

## 5. 権限を確認して承認する

実行待ちの ToDo に「必要な権限を調べる」が出る。
押すと Authorization Platform が、書かれたタイトルと説明と、ログインユーザーが持つ Human Permission、組織のポリシー、リスクのポリシーを突き合わせ、許可する操作と隔離のレベルを決める。
結果は Agent Definition として画面に出る。

許可される操作は、決まったままの文字列で並ぶ。
Automation App はこの文字列の意味を持たず、言い換えも並べ替えもしない（[10. 設計ルール](./10-design-rules.md) の RULE-07）。

「この権限で承認する」を押すまで Agent は作られない。
承認した時点で、提示された操作の一覧がハッシュとして記録される。

続けて「この内容で Agent を作る」を押すと Agent Provisioner が Agent を作り、画面はその Agent の画面へ移る。
承認から作成までの間に必要な権限が変わっていた場合、作成は断られる。
その場合は提示され直した内容を読み、承認からやり直す。

作られた Agent には、確定した ToDo の内容（タイトル、説明、実行時のコンテキスト、完了条件、手順、注意点、優先度、期限）が1件目の指示として渡る。
Agent はこれを読んで最初の Tool を選び、完了条件を満たしたら作業を終える。
渡るのは文章だけで、承認した権限は変わらない。
Agent ができると ToDo は「実行中」になり、カードにその Agent へのリンクと状態が出る。

外部 SaaS を使う自動化を `enable_google_bridge=true` で動かしている場合は、ここで同意画面の URL へ飛ぶ。
同意すると元の画面へ戻り、続きが進む。

## 6. 動いている Agent を操作する

作られた Agent は ToDo のカードと「3. 動き出した Agent」に並ぶ。
名前をクリックすると Agent の画面（`/agents/{agent_id}`）へ移る。

この画面でできることは4つである。

- 状況確認：いまの状態、残り時間、実行中の Task、使った Tool とその結果が出る。実行中のものを含む今の断面である。
- 実行ログ：Agent が1手ごとに、どの Tool を選び、どこへ何を送り、何が返り、送る前に何を確かめたかが出る。Agent 自身がその手で書いた文章もそのまま載る。Task が終わるのを待たずに読める（[11. §5.5](./11-activity-timeline.md#55-agent画面の実行ログ)）。
- 追加指示：「指示を追加する」で、動いている Agent に伝えることを足す。承認した権限の外の操作は、指示しても Tool Executor が実行を断る。
- 停止：「この Agent を止める」で即座に止まる。止めた Agent は元に戻せない。同じ作業をさせるには、作業を書くところからやり直す。

権限を増やす操作はどこにも無い。
作られた Agent の権限はその生涯にわたって変わらないためで、足りなければ新しい Agent を作る（[02. §5](./02-automation-design.md#5-実行中agentの操作)）。

Agent は希望した時間を過ぎると自動で消える。
分単位で指定でき、上限は1440分（24時間）である（[07. Lifecycle](./07-lifecycle.md)）。

### 6.5 ToDo を閉じる

Agent が作業を終えると、ToDo のカードに Agent Runtime の判定が出る。
「指示された作業を最後まで行いました」「権限の範囲外の操作があったため、そこで止めました」「途中で問題が起きたため、作業を完了できませんでした」の3つのどれかで、詳しくはタイムラインで読める。

結果を読んで、済んだと判断したら「完了にする」を押す。
ToDo を閉じるのは Agent ではなく、あなたである。
Agent が完了を報告しても ToDo は自動では閉じない。

「取り下げる」は Agent が止まってから押せる。
Agent が `ACTIVE` の間は断られるので、先に Agent の画面で止める。
完了も取り下げも元に戻せない。
閉じた ToDo は一覧の下の「終わった ToDo」に畳まれる。

## 7. 実行の様子を見る

結果別フィルターと検索で、作業名、Agent、Task IDを絞り込める。
「更新」は選択中のAgentに絞ったまま新しい記録を取得する。

`/activity` は、ログイン、権限の決定、Agent の作成、Tool の呼び出し、停止までを時系列で見せる。
Agent ごとにまとまり、新しい Agent が上に来る。ログインから、作業を書き、Authorization Platform に権限を尋ね、承認し、Agent が動き、止まるまでが1つの Agent の物語として並ぶ。
1つの Agent の中は「動きを見る」と「やったこと」の2段で、終わった Task の再生をまとめて先に並べ、そのあとに同じ Task の文章が同じ順で続く（[11. §5.1](./11-activity-timeline.md#51-画面の構成)）。

画面の先頭に「この記録に出てくるもの」がある。
その記録に登場したものだけを並べ、名前・何をするところか・すること・**しないこと** の4つを書いている。
Agent OP や Resource AS が何なのか分からないまま図を見ても、矢印が手前で止まった意味は読み取れない。
図の箱を押しても同じ説明が出る。

図には、その処理に関わったものだけが箱として出る。
1回の Tool 呼び出しは1本の矢印ではなく、Agent OP が身元を出し、Resource AS が Access Token に換え、Resource API が答える、という往復として順に動く。
遮断された処理は、経路が宛先の手前で止まる動きで示され、届かなかった箱は点線のまま残る。
1手は4〜5秒かけて進み、動きが終わったあとは絵が止まったまま残るので、添えられた文はその間に読める。
「一時停止」で止まり、「次へ」で1つずつ進められる。

図の右（画面が狭いときは下）に「この手で Agent が考えたこと」が出る。
再生している1手について、**読み取ったこと**（その手で読んだ指示）、**考えたこと**（Agent 自身の言葉、そのままの引用）、**決めたこと**（選んだ Tool と渡そうとした引数）、**実行前に確かめたこと**（許可・有効期限・条件と、その判定）が順に出る。
どれもそれを行った側がその場で書いた文章であり、画面が要約したものではない。

「やったこと」には、同じ内容が Task ごとに文章で出る。
各行の頭に、それを行った箱の名前と、その箱が何をするところかが並ぶ。
1件ごとに、実行前に確かめたこと、送ったリクエスト、返ってきた値、そして Agent 自身が書いた文章が読める。
図を再生している間は、その Task の文章のうち、いま説明している行が強調される。
Authorization Platform の行を開くと、AI が作業をどう読み、何を提案し、Policy Engine がそれぞれをなぜ許可し却下したかが出る。

再生できるのは終わった Task だけである。
動いている最中のものは名前だけが出る。
途中経過を見たいときは Agent の画面の実行ログを使う（[11. アクティビティタイムライン](./11-activity-timeline.md)）。

画面は自分の記録だけを見せる。
他の利用者のログインや Agent は、同じ画面のどこにも出ない。

### 7.1 遮断を再現して見る

権限の外の操作が止まる様子を、実際に危険な操作をせずに見せたい場合、記録済みの台本を自分のタイムラインへ流し込める。
画面にはボタンが無いため、ログイン済みのブラウザから次を実行する。

```javascript
await fetch('/api/demo/replay', {
  method: 'POST',
  credentials: 'same-origin',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ scenario_id: 'dpop-replay' }),
});
```

`scenario_id` に指定できるのは `dpop-replay`、`cross-agent-isolation`、`delegation-mismatch`、`signing-key-misuse` の4つである。
流し込んだ Task には「デモ実行（模擬）」の印が常に付き、実際に起きたこととは区別される。
Agent の状態は変わらず、Security Detection にも何も届かない。

### 7.2 実際の実行失敗を試す

デモ環境では、Agentの画面に「異常系を試す」が表示される。
実行中のAgentで「このAgentの実行を失敗させる」にチェックし、「実行失敗を発生させる」を押す。
要求を受け付けると、対象のTaskが次の推論ステップで要求を読み取り、例外を発生させる。
状況確認は5秒ごとに更新され、「異常系試験の状態」に要求IDと対象Task、適用状況を表示する。
要求は「適用待ち」から「Runtimeが受信済み」へ進み、要求IDに一致する失敗を確認すると「実行の失敗を確認」と表示する。
実行が先に終わった要求は未適用と表示され、次のTaskへの試験要求を妨げない。
受信済みでも失敗の記録が確認できない場合や、後続の実行で状況が更新された場合は、アクティビティで結果を確認する。
Runtimeは `TASK_FAILED` を発行して終了コード30で終了するため、アクティビティにも失敗が表示される。

失敗するのは実行であって、Agentそのものの状態ではない。
状態は Lifecycle の値（[07. §2](./07-lifecycle.md#2-lifecycle状態)）のままで、`ACTIVE` と表示される。
Agentごと止めたい場合は「この Agent を止める」を使う。

要求はログインした本人の実行中Taskに限定され、同じ要求の重複登録は拒否される。
すでに実行が終了している場合や、外部呼び出しで処理が止まっている場合は、その場では適用されない。
後続の別Taskには適用されない。
資格情報の失効も含めて試す場合は、通常の停止操作を使う。

この機能はAutomation Appの `ENABLE_FAULT_INJECTION=true` で有効になる。
未設定時は画面にもAPIにも公開されない。
`infra/envs/demo` とローカル実行環境は有効に設定している。

### 7.3 ログ分析の状態と判断を確認する

画面上部の「ログ分析モニター」から `/security` を開く。
自分のログに関連する最新30件について、受信、正規化、違反確認、ルール検知、相関分析、スコア判定、AI分析、対応判定を確認できる。
AI分析中は、モデルの回答を待っている間もその状態と経過時間が表示される。
進捗バーに完了した段階数を、各段階に所要時間を表示する。
所要時間には分析記録の保存待ちも含まれる。

AI分析が起動するのは、検知結果のスコアが30以上で、Agentの比較基準とAI接続がそろっている場合である。
各判定には、検知コード、スコア、起動または省略の理由、推奨状態、確信度、Lifecycle Managerへの依頼結果を表示する。
「スコアの算出根拠」を開くと、判定時点の要因ごとの該当数、重み、上限、加点を確認できる。
該当数は生ログの件数ではなく、スコア計算に使った検知コードの数である。
リソースへの加点は、対象へのアクセス有無で決まる。
委任の不一致や署名鍵の不正使用によって100点となった場合は、通常の加算とは別の判定条件も表示する。
過去の記録に内訳や所要時間がない場合は、現在の条件から再計算しない。
確信度が70%未満の場合、隔離や失効や破棄の推奨、AI回答を利用できなかった場合は、人の確認を待つ。
この画面は分析実行時点の判断記録であり、その後の人による承認状況は含まない。
署名鍵の目的外使用を調べる定期バッチは、この画面の監視対象に含まない。

状況は5秒ごとに取得され、自動更新のチェックを外すと手動更新に切り替わる。
Reactの状態を更新して表示し、展開した詳細や入力中の操作欄を保持する。
処理中の記録が60秒以上更新されなければ、遅延または中断の可能性を表示する。
記録がない状態では、サービスが正常稼働しているかは判断できない。
表示する分析記録に生ログ、認証情報、AIへのプロンプトは含めない。

分析記録は `security_analysis` に保存し、7日後をTTLの期限とする。
デモ環境のTerraformには、自分の最新30件を取得するインデックスとTTL設定を追加している。
画面とサービスを更新するときは、このTerraform変更も適用する。

### 7.5 他のツールから ToDo を登録する

ToDo は `POST /external/todos` でも登録できる。
必要なのは Human IdP が発行した Automation App 宛のアクセストークンで、`Authorization: Bearer` に付ける。
画面の Session は要らない。

```bash
curl -sS -X POST "$AUTOMATION_APP_URL/external/todos" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title": "未処理の経費申請を確認する", "context": "申請書は経理フォルダの「未処理」にある", "done_criteria": ["10万円超の一覧が書かれている"], "priority": "high", "due_on": "2026-09-30"}'
```

トークンは、Human IdP の `automation-app` クライアントで `agent:operate` スコープを要求して得る（`aud=automation-app`）。
項目は画面と同じで、必須なのは `title` だけである。
`GET /external/todos` で自分の ToDo の一覧、`GET /external/todos/{id}` で1件が読める。

API で登録できるのは下書きまでである。
確定、承認、Agent の作成はこの画面で行う。
API から登録した ToDo は、一覧に「API から登録」と印が付く（[02. §6](./02-automation-design.md#6-todo登録api)）。

[review-markdown-cli](https://github.com/maronnjapan/review-markdown-cli) との連携は、この API を使う例の一つで、このリポジトリの `pnpm review:import` が担う。
レビュー中に「やると決めた」タスクを読み取り、下書きの ToDo としてここへ登録する。
連携のためのコードはこのリポジトリ側にあり、review-markdown-cli はこの基盤の URL もトークンも持たない。
手順は[review-markdown-cli から ToDo を取り込む](./review-markdown-import.md)にある。

## 8. 分析エージェントの判断を見る

Agent が動いている間、ログを分析するエージェントがその挙動を見ている。
異常と判断すれば Agent は隔離され、判断が曖昧なときは人の確認へ回る（[09. §6](./09-security-monitoring.md#6-response)）。
その判断を読む画面は **Analysis Console** で、Automation App とは別のサイトである。
Automation App の上部にある「分析エージェントの判断」から開ける。

別サイトなので、初回は同じユーザー名とパスワードでもう一度ログインする。
このログインで得られるのは名前だけで、Agent を作る・止めるといった権限は一切付かない（[09. §7.1](./09-security-monitoring.md#71-analysis-console)）。

Agent ごとにまとまり、そのAgentが今どの状態か（`ACTIVE`、`QUARANTINED` など）が見出しの下に出る。
Agent 名を押すと Automation App の Agent 画面へ戻る。

1件ごとに次が出る。

- リスクの高さとスコア、いつの区間を見ていたか、どのルールが反応したか。
- 分析エージェントの回答そのもの：通常との差、権限との整合、侵害の可能性、誤検知の可能性、出来事のつながり、影響の範囲、他の OP への波及。
- 推奨する対応と確信度、そして人による確認が要るかどうか。

「判断の出どころ」に「リスク値だけで決めた既定の対応」と出ることがある。
分析エージェントから読み取れる回答が返らず、スコアだけで既定の対応を選んだという意味で、何かが推論した結論ではない。
この場合は必ず人の確認へ回る。

何も記録されていない Agent も一覧に残り、「気になる挙動は記録されていません」と出る。
出ないことと、見られていないことは別だからである。

この画面は表示だけを行う。
承認・却下・停止のボタンは無く、Agent を止めるのは §6 の Agent 画面である。
表示するのは自分の Agent だけで、他の利用者の Agent は出ない。

分析エージェントが何も記録していない Agent は並ばない。
この画面は Agent の一覧ではなく、判断の一覧だからである。
Agent の一覧は Automation App にある。

## 9. うまくいかないとき

| 症状 | 原因 | すること |
|---|---|---|
| 「必要な権限を調べる」の結果が空、または却下ばかり | ログインユーザーの Human Permission が空 | §1 の `pnpm perm:set` で付ける |
| 「この内容で Agent を作る」が断られる | 承認したあとに必要な権限が変わった | 提示され直した内容を読み、承認からやり直す |
| Agent が Tool の実行を断られた | 承認した権限の外の操作だった | ToDo を書き直し、新しい Agent を作る |
| 「取り下げる」が `agent_still_running` で断られる | その ToDo の Agent がまだ動いている | Agent の画面で止めてから、もう一度押す |
| `/external/todos` が `401` になる | トークンが無い、期限切れ、または宛先が `automation-app` ではない | `agent:operate` スコープで取り直したアクセストークンを `Bearer` で付ける |
| Agent の使った Tool が `unknown` `failed` `invalid_tool_call` ばかり | 古い版で Agent が Tool を選べなかった | 最新の版を配備し直す（`scripts/deploy-gcp-guide.sh all`） |
| 「この Agent を止める」が `invalid_token` になる | 古い版で停止要求の鍵の取得先が違った。またはログインから1時間が過ぎた | 最新の版を配備し直し、ログインし直す |
| タイムラインに何も出ない | 終わった Task が無い | Agent の画面の状況確認で今の状態を見る |
| Analysis Console に何も出ない | まだ Agent が無いか、分析エージェントが何も記録していない | 何も記録が無いのは正常な状態である |
| Analysis Console でログインを求められる | Automation App とは別のサイトで、Session も別である | 同じユーザー名とパスワードでログインする |
| 画面がログイン画面へ戻る | セッションが切れた | もう一度ログインする |

## 10. 片付ける

Automation App と Human IdP はインターネットへ公開され、ログイン情報は固定である。
確認が終わったら破棄する。

```bash
PROJECT_ID=<project-id> make demo-destroy   # アプリだけを消す
PROJECT_ID=<project-id> make destroy-all    # プロジェクト以外を全部消す
```

作り直すときは `scripts/deploy-gcp-guide.sh all` を実行する。
